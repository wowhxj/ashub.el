# ashub 会话一句话摘要需求

## 问题与目标

ashub 当前列表展示用户首句和末句，不能直接说明整段会话的主题与进展。新增一句话摘要，让用户快速判断会话做了什么、进行到哪里，以及是否值得打开或恢复。

本文记录讨论结果，不是实施计划。明确区分用户确认的要求、建议策略和待验证问题。

---

## 已确认需求

**摘要与模型**

- R1. 每个纳入范围且可读取的会话生成一句中文短话，兼顾主题与当前进展，而不只是重写首条提问；保留必要的技术名词。
- R2. 复用 Emacs 中 gptel 的配置，使用 gptel 默认模型；不要求用户为 ashub 维护另一套模型配置。
- R3. 摘要是 ashub 的独立派生信息，不修改原 agent 的对话记录或标题。

**后台维护**

- R4. 摘要需要后台自动生成、自动更新，不依赖用户逐个手动触发。
- R5. Emacs 内已经打开、仍在使用的 agent session 不得更新摘要；停止使用后等待可配置的时长再处理，默认 5 分钟。等待期间重新打开则跳过，之后再次停止使用时重新等待。不能仅凭暂时没有新消息就认定其未被使用。
- R6. 使用状态的识别范围仅限 Emacs，不要求检测外部终端中的 agent。
- R7. 全部普通及归档历史会话需要缓慢后台补齐，不限于当前屏幕可见的会话；排除内部和空会话。
- R8. 后台维护应无感，不阻塞浏览和正常使用。成本控制主要通过减少不必要的模型调用实现，而不是压缩单次请求内容；摘要质量优先。摘要队列单并发，相邻两次请求发起时间至少间隔可配置的时长，默认 60 秒；上一个请求未结束时不发起下一个。
- R9. 已有摘要且会话正文未变化时，不重复调用模型；使用期间发生的多次变化应尽量合并处理，而非逐轮生成。

**列表展示**

- R10. 列表正文展示三列：摘要、用户末句、摘要状态。摘要列优先显示一句话 AI 摘要，用户末句始终独立展示，状态不混进两列正文。
- R11. 原始首句和末句保留在会话详情中，不与 AI 摘要混淆。
- R12. 尚无成功生成的摘要时，摘要列仅回退显示用户首句，不再拼接末句；末句仍展示在独立列。后台生成不阻塞浏览，状态列明确区分待生成、生成中、已生成、待更新、失败及模式停用/暂停。

**可配置性与摘要质量**

- R13. 各类时间参数都必须提供可在 Emacs 配置文件中设置的用户变量，不写死。包括停止使用后的等待时长、请求最小间隔，以及实现中需要的后台检查周期、正文稳定窗口、请求超时和失败重试时间等。5 分钟、60 秒仅为默认值，其余默认值在规划时确定。
- R14. 每次摘要尽可能使用完整、相关的会话内容，以提升主题与进展判断的质量。不为节省单次 token 而默认裁剪首尾、限制为少量轮次，或以旧摘要加新增对话代替完整会话。工具结果若关系到执行、测试或验证结论，也应作为相关证据保留；内容选择以相关性与摘要质量为依据。
- R15. 若会话超出默认模型的上下文或服务请求限制，应明确设计保留关键信息的处理方式，并验证摘要质量；这是技术限制下的适配，不是以省 token 为目的的主动删减。

## 验收示例

- AE1. **Covers R1, R3.** 会话讨论项目改名后的 Pi 会话恢复问题，已调整代码但尚未验证；摘要应类似“修复项目改名导致的 Pi 会话恢复失败，代码已调整，待验证”，不能写成“问题已彻底解决”。原始会话不变。
- AE2. **Covers R5, R9, R13.** 会话在 Emacs 中保持打开，即使长时间没有新消息，也不生成或更新。退出使用满配置的等待时长后，才有资格处理其累积变化；默认等待 5 分钟，若配置改为 10 分钟，则按 10 分钟执行。等待期间重新打开，不发出请求。
- AE3. **Covers R7, R8, R9.** 首次启用时历史会话逐步补齐，而不是并发发出大量请求；再次检查未变化的已摘要会话不产生新的模型调用。
- AE4. **Covers R10, R11, R12.** 无摘要时第一列仅显示用户首句，第二列显示用户末句，第三列显示待生成或相关状态；生成成功后仅第一列替换成 AI 摘要、第三列变为已生成，第二列仍保留末句。三个列头与内容在宽窄窗口均对齐，完整文本可通过 tooltip 和详情查看。
- AE5. **Covers R8, R13.** 在配置文件中修改请求间隔、检查周期、超时和重试时间后，各自行为遵循配置，不存在绕过用户变量的固定调度值。配置生效方式需在规划和使用说明中明确。
- AE6. **Covers R14, R15.** 会话中间曾推翻最初方案，并通过工具测试验证最终修复；只要模型上下文允许，请求不能为节省 token 而只发送首尾或旧摘要。最终摘要应反映最终方案与真实验证状态。

## 建议策略：尚非用户确认的固定要求

- 在 Emacs 运行期间独立维护后台队列，不要求 ashub 列表一直打开。
- 若停止使用后的等待期间正文继续变化，建议同时等待正文稳定，避免处理仍在写入的内容；如引入独立稳定窗口，该时长也必须可配置。单并发已确认；请求最小间隔默认 60 秒，停止使用后等待默认 5 分钟，两者均为可配置变量。
- 优先处理近期变化，其次补历史；兼顾历史队列最终能继续推进，避免持续被新会话挤占。
- 摘要和处理进度持久化，重启 Emacs 后继续补齐，避免重复调用。
- 首次生成和后续更新都优先使用完整、相关的会话内容，而不是默认增量总结。可识别新增内容以判断是否需要调用，但不能将增量检测等同于仅发送增量。
- 输入整理以保留主题、决策变化和执行验证证据为目标，不机械删除工具结果；旧摘要可用于展示，但不能取代完整历史作为唯一背景。
- 摘要只能表达输入证据支持的进展，区分计划、执行、测试、验证，不夸大完成程度。
- 发起请求前复核使用状态；生成期间若重新打开或正文变化，结果不得直接标成最新。
- 请求失败保留旧摘要、退避重试，通过诊断查看问题，不频繁弹窗；重试相关时间必须可配置，并避免无节制重试。
- 切换 gptel 默认模型不自动重做全部历史摘要；可考虑提供手动强制重生成入口。

## 成功标准与成本边界

- 用户通过列表主列即可辨认会话主题与当前进展，不必逐个打开对话。
- Emacs 内打开的 session 不触发摘要更新。
- 已摘要且内容未变的会话不消耗新的摘要请求。
- 历史会话可以渐进补齐，后台工作不拖慢交互。
- 省 token 的主要手段是避免不必要的调用：正文未变不调用、使用期间合并变化、持久化缓存避免重启后重复生成、失败重试有节制。仅降低请求频率不等于减少总调用次数。
- 单次调用以摘要质量为先，接受为完整、相关上下文消耗更多 token；不把输入裁剪率或单次 token 最少作为优化目标。只有模型上下文等技术限制要求时才适配超长输入，并验证质量。
- 各类时间均通过用户变量配置；已讨论数值仅为默认值，不能成为不可调整的硬编码。
- gptel 默认模型决定实际单价与能力，ashub 无法保证默认模型本身便宜，也不能保证模型完全不产生额外推理 token。

---

## 范围边界

- 不独立选择或维护另一套摘要模型配置。
- 不检测 Emacs 外部终端会话的使用状态。
- 不向原 session 发送摘要请求，不改写原 agent 历史。
- 不扩展为长篇报告、知识库或任务管理系统。
- 本轮仅讨论与记录需求，未实施代码，也未发起模型请求。

## 依赖与待明确事项

### Resolve Before Planning

无已识别的阻塞项。模型入口、使用状态范围、可配置时间及其已选默认值、输出语言、历史范围与列表展示方式均已确认；成本控制以减少不必要调用为主，单次输入以摘要质量优先。

### Deferred to Planning

- 首次启用与自动维护的开关方式；在没有可用 gptel 配置时不得盲目重复请求。
- 一句话摘要的具体输出长度；生成期间、失败和内容变化后旧摘要的轻量提示方式。
- 时间用户变量的名称、默认值、合法范围和配置生效方式；除已确认的默认等待 5 分钟、请求间隔 60 秒外，其他默认时间由规划确定。
- 正文无法读取的来源如何回退展示与诊断，不能虚构摘要。
- 完整会话输入的质量验证；只有超过模型上下文或服务限制时才设计超长会话适配，不能以节省单次 token 为由默认裁剪或增量总结。

### 规划时验证的技术问题

- gptel 默认配置在后台调用中的解析上下文、异步调用、超时、取消和错误处理能力；避免意外附带额外上下文或工具能力。
- 复用现有 Emacs live session 判断时，各 agent 的打开、关闭、进程结束、buffer 残留如何映射到使用状态。
- 各会话来源完整内容读取、相关工具证据提取、分支语义及历史改写的可靠性；变化检测用于避免无效调用，不意味着摘要请求只发送增量。
- 如何低成本区分正文变化与仅元数据变化；如何持久化缓存并防止并发或重复请求。
- 如果请求已发出后会话重新打开，能否取消；不能把取消等同于已经避免服务商计费。
